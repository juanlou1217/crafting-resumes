# 技术与数据岗位 Playbook

适用于软件工程、前端、后端、测试、数据与 AI 岗位。先以用户提供的 JD 和已确认事实为准，再按 `experience-interview.md` 用所有可见线索推演完整候选业务逻辑，用本表选择进入具体问题后的追问方向。

## 使用硬门

下表的关键词、指标、项目和问题都只是追问方向，绝不是候选人事实。不得据此补工具、模块、架构、数据、数字、上线状态或结果。真实性门与单问题门优先于岗位匹配：只有 `confirmed` 事实可进入候选人事实产物；证据不足且影响下一步时，每轮正好问一个最高信息增益问题，不输出待用户套用的“完整 bullet”。

**岗位词汇方向（仅用于提问与写作选择）**：问题定位、约束识别、接口边界、设计取舍、失败处理、测试验证、策略演化、数据分析、模型评测、工程落地。它们只是问题与表达方向，不是候选人事实；工具名、岗位常用词或 JD 出现都不能代替候选人的上下文、判断、口径与归因证据。

工具名只说明接触过某种工具，不证明设计深度、熟练度、规模或业务影响。公司经历先恢复什么客户/经营/运营/风险信号触发投入、为什么当时优先、影响对象与规模、公司价值机制，再挖掘技术工作试图改变的问题、当时定位依据、约束与真实取舍、策略如何演化、验证基线、结果口径和复盘。候选人不必拥有公司优先级决策权，但必须区分已知的组织理由与本人的技术判断。本人模块与团队边界只在贡献措辞、结果归因或真实性需要时核实，不把代码量或亲自完成范围当成经历价值。

## 岗位追问方向

| 岗位族 | 优先核实的证据 | 可追问指标或代理 | 禁止捷径 |
| --- | --- | --- | --- |
| 软件工程 | 触发改动的故障、摩擦或能力缺口；定位依据；依赖与约束；关键机制/数据流；方案取舍；验证和复盘 | 交付状态、覆盖范围、缺陷类型、响应时间、资源或成本；均须确认口径 | 把实现清单当问题深度；把参与开发写成系统负责人；把库名或 API 当机制深度 |
| 前端 | 用户或产品流程中的摩擦；交互、状态和数据流为何成为突破口；关键机制、兼容/性能约束；方案演化与验证 | 可验证的加载表现、错误类型、操作步骤、复用范围、交付效率、验收结果 | 只列页面、React/Vue、API 或类比；由页面数量推断复杂度、机制深度或业务增长 |
| 后端 | 服务行为或上下游约束中的真实问题；数据、并发、一致性或故障判断；方案取舍、验证与失败处理 | 吞吐、延迟、可用性、故障、任务耗时、成本；须说明环境与时间窗 | 由 Java/Python/框架名推断微服务、架构所有权或线上规模 |
| 测试 | 哪类质量风险最值得阻断；依据什么排序；用例/自动化策略如何在漏测、成本或发布压力下调整 | 覆盖范围、缺陷类型、执行耗时、回归频率、发布验收 | 把执行用例写成质量治理；把团队线上稳定性归为个人 |
| 数据 | 业务问题、指标定义、数据来源、清洗/查询/分析方法、基线、结论与采用边界 | 查询效率、看板/分析覆盖、实验结果、建议采用；区分相关与因果 | 只列 SQL/Python/BI；把报表产出直接写成增长或决策影响 |
| AI / 算法 | 问题定义、数据与标注、基线、模型/方案取舍、评测、部署或应用边界、失败分析 | 准确率/召回率/F1、任务成功率、延迟、成本、人工兜底；须核实评测集和归因 | 调用 API 不等于算法或 AI 任职；未确认不得补 Agent、RAG、训练、评测或商业落地 |

## 证据选择顺序

1. 汇总用户提供的代码、工具、任务、反馈、指标、协作、时间节点或交付物等全部线索，先推演 2–4 条由组织触发贯通到验证证据的完整候选业务逻辑，帮助用户识别真实上下文；不得只给零散价值角度。
2. 公司经历先确认进入优先级的触发源与来源，再确认为什么现在先做、影响哪些账户/角色/用户/业务量，以及公司通过何种机制获得或保护价值。“客户反馈了”只说明线索来源，不自动说明为什么值得投入。
3. 确认真正的产品/技术问题、重要性与当时的定位依据；“被要求开发”或“最佳实践”不能替代问题定义。
4. 确认一个能体现判断的约束、真实备选方案、关键介入或策略调整。
5. 确认测试、实验或验收基线；“做完”“上线”不自动证明质量或影响。
6. 确认交付、采用、产品/运营和公司价值各层的结果来源、时间窗、因果边界与复盘。团队性能、业务指标或公司结果不能自动归到个人。
7. 只有最终贡献措辞或因果归因需要时，再确认最小职责边界；不要把这一步重复成访谈主线。

## 单问题选择

优先问会改变“公司为何投入、为什么优先、影响规模、价值机制、问题解释、判断深度、策略演化、结果可信度或能否写”的一个未知。若只知道工具或开发任务，先推演少量完整候选业务逻辑，再优先区分真实触发信号；不要先问实现细节。触发和优先级清楚后再进入问题判断、关键机制与取舍；若已有结果数字，先问口径和归因。只有强贡献动词缺少边界时才问最小职责范围。每轮只能选择其中一项，不拼成技术问卷。
