# Experience Interview

## Objective

在写作前最大化已验证的信息增益，并把零散任务、代码、反馈、数据、协作、文档或交付物挖掘成一段贯通公司选择与问题解决的完整经历。访谈的主目标不是盘点“做了什么”，而是帮助用户恢复组织为什么投入、价值如何发生，以及当时的问题、判断、取舍、变化与学习。访谈仍需继续时，每轮只问且正好问一个问题；不要为了尽快产出而把线索补成事实。

若现有事实不足以形成可投递经历，先明确说明这一阻断，不先写“强 bullet”、候选成句或加入未确认动作。只有 `confirmed` 事实才可进入候选人事实产物。

STAR 只用于把已经核实的经历压缩成易讲述的摘要，不是经历准备的底稿。不得从 Situation、Task、Action、Result 四个槽位倒推或补齐事实；公司/商业经历先建立公司级业务案，再完成下面的四层经历地图，最后按用户需要压缩为 STAR、简历 bullet 或面试回答。

## 默认分析单位与由外到内主链

公司经历的默认分析单位不是“一个开发任务”或“一个项目”，而是公司在有限资源下作出的一次投入选择。所有线索都沿同一条主链组织：

```text
组织选择：公司为什么投入，为什么现在先做
  -> 业务系统：影响谁、影响多大、价值或损失通过什么机制发生
  -> 问题系统：什么瓶颈、约束或根因阻断了预期价值
  -> 问题解决：判断、取舍、关键介入、调整与复盘
  -> 分层证据：交付/采用、行为、产品或运营指标、公司价值、财务或战略结果
```

这不是要求每段经历都拥有收入数字，也不是让开发者冒充公司决策者。它要求 Skill 先恢复组织为什么愿意做这件事，再判断候选人在其中体现了什么思考。某层未知时，主动形成可证伪的完整候选逻辑帮助用户回忆；不能退回局部产物罗列，也不能跳过中间机制直接宣称公司价值。

## 公司级外层：业务案

四层地图解释“一个问题如何被判断、解决与验证”；公司级业务案先解释“为什么组织愿意为它分配资源”。它是四层之外的上游语境，不是把四层改成五层，也不等于要求候选人拥有公司决策权。开发者可以基于自己当时确知的 PM、负责人、客户成功、销售、支持团队、客户或决策材料说明公司理由，并记录来源；只有候选人确实参与优先级或经营决策时，才能把该判断写成本人动作。

公司、商业产品或正式组织内的经历维护 `company_context_map`；课程、个人、开源或确实没有公司语境的经历，将客观不适用字段记为 `N/A：原因`。

| 字段 | 要恢复的公司级问题 | 常见但必须核实的线索 |
| --- | --- | --- |
| `strategic_context` | 当时公司、业务线或产品要实现什么更高层目标，这项工作连接哪项客户承诺、产品策略、运营目标或风险要求 | 产品路线、平台化方向、重点客户策略、增长/留存目标、成本治理、SLA/合规；路线名称不能替代实际关联 |
| `demand_trigger` | 什么信号让问题进入组织视野，而不是“有人提了需求”就结束 | 客户/CS/支持反馈、被阻塞的成交或续约、漏斗/使用数据、事故与 SLA、人工成本、监管、竞争或平台变化 |
| `why_now_priority` | 为什么当时先做它而不是其他事项，真实比较维度、依赖和机会成本是什么 | 影响与覆盖、紧迫性、置信度、投入、关键依赖、客户承诺、风险窗口；不得倒推团队使用过 RICE 等框架 |
| `stakeholder_reach` | 谁提出、谁决策、谁交付、谁被改变，以及实际影响规模是多少 | 分开记录请求/决策方、实施协作方、内部使用角色、客户账户/品牌、终端用户、申请/交易/工单量；团队人数不等于用户规模，品牌数不等于采用人数 |
| `value_capture` | 工作完成后，公司通过什么机制获得价值，不强迫所有项目换算收入 | 新增收入、保护续约/存量收入、销售解锁、采用/漏斗改善、支持或人工成本下降、SLA/合规/声誉风险下降、平台复用与边际接入成本下降、战略选择权 |
| `counterfactual_opportunity_cost` | 如果不做会发生什么；为了做它推迟或放弃了什么 | 已知客户/用户损失、继续存在的成本/风险、关键项目依赖受阻、其他需求延期；没有比较信息就记录未知 |
| `post_delivery_business_evidence` | 交付后有什么证据说明预期价值真的发生，证据处于价值链哪一层 | 实际采用/覆盖、行为或漏斗变化、工单/人工时变化、客户反馈、合同/续约/收入、风险事件；交付与上线只证明交付状态 |

公司级事实同样使用四种证据状态。用户知道公司为什么做但不是决策者，并不降低经历价值；应写成已确认的业务背景或组织判断，不写成“我决定公司优先做”。如果用户只知道局部材料，先推演 2–4 条贯通组织触发、优先级、影响规模、价值机制、具体问题和验证信号的完整候选业务逻辑，再用一个问题区分真实解释；不得把候选逻辑直接升级为经历结论。

## 四层经历地图

围绕一个真实问题维护同一张地图。四层是依赖链，不是四段文案：如果“问题”没有被定义清楚，后面的判断、动作和结果就无法可靠解释。

| 层 | 覆盖字段 | 要验证的核心 |
| --- | --- | --- |
| `problem` | `core_problem`、`priority_counterfactual` | 真正需要改变的状态是什么；为什么它比相邻问题更值得解决；不处理会造成什么已知影响。上级分配的任务、功能需求或 KPI 不是自动成立的问题定义 |
| `judgment` | `diagnostic_basis`、`alternatives_tradeoff` | 候选人当时依据哪些数据、用户反馈、观察或约束定位问题；比较过哪些真实备选方案；为什么做出该取舍。事后解释不能冒充当时判断 |
| `action` | `key_intervention`、`strategy_evolution`、`resistance_adjustment` | 哪个关键介入改变了问题状态；策略如何从初始方案演化；遇到的真实阻力、失败或质疑；获得新证据后如何调整。实现细节只有在能解释判断、约束、取舍或结果时才继续深挖 |
| `result` | `outcome_evidence`、`causal_attribution`、`retrospective_counterfactual` | 结果、交付或变化如何定义和证明；哪些证据能把变化与本人动作连接，哪些只是同期发生；外部因素和团队贡献是什么；重来会保留或改变什么及其依据 |

另维护横跨四层的 `fact_details`：时间、规模、指标口径、协作对象、职责边界、关键机制、关键节点、证据来源和公开边界。事实细节是交叉校验与安全层，不是访谈叙事主线；只有当职责会改变贡献措辞、结果归因或真实性时才追问个人边界，不得反复要求用户证明“亲自完成”。也不得为了显得完整而补数字、工具、日期或角色。

每个字段记录 `confirmed`、`pending_confirmation`、`model_inference`、`conflict` 或明确未知。用户一次回答覆盖多个字段时全部更新；不要强迫真实经历具备不存在的备选方案、失败或量化结果。用户明确确认“当时没有比较其他方案”“未统计结果”或“不适用”本身可以成为该字段的已确认结论。

## 业务链与技术/方法链

公司经历的深度来自两条相接的链，不能用其中一条冒充另一条：

- **业务链**：组织触发 → 优先级 → 受影响对象与规模 → 价值机制 → 交付后的分层证据。
- **技术/方法链**：问题现象 → 原因与约束 → 关键机制/实现 → 真实备选与取舍 → 测试、验证和失败边界。

只会复述现象、API、工具清单或类比，不能证明理解了关键机制；只会描述机制，也不能自动证明公司价值。若存在被采用的复用组件、流程、文档或其他资产，将其作为结果或复盘证据，另行核实采用范围和归因。没有更深证据时降级表述，不引导用户背诵虚构细节。

## 七类深挖问题背后的风险

- **核心问题**防止把“接到什么任务”写成“发现并解决了什么问题”。若不知道为何重要，经历只能证明执行，不能证明优先级判断。
- **判断依据**防止事后诸葛亮。没有当时可见的证据，就不能把最终正确结果反向包装成高质量判断。
- **备选方案**检验决策而非列方案数量。只有真实考虑过的选择、约束和取舍才可记录；没有备选时保持没有，不能为了面试感编出 A/B/C。
- **阻力与调整**区分机械执行和问题求解。关键不在“遇到困难”这句，而在新信息如何改变了动作、范围、节奏或协作方式。
- **结果归因**防止把相关性写成因果。前后变化、上线、市场增长或团队成果不能单独证明由本人动作导致；要核实机制、时间关系、对照、过程证据和外部因素。
- **复盘反思**检验学习是否来自真实经历。泛泛说“沟通要更早”没有价值；要指出哪个判断、假设或动作会改变，以及为什么。
- **事实细节**检验整条故事能否承受追问。时间、规模、指标、协作对象和关键节点互相矛盾时，先处理冲突，不用流畅措辞掩盖。

## 从多种线索反推完整经历

无论用户给出的是代码、任务、客户反馈、事故、指标、时间节点、协作关系、上线记录还是交付物，都不要把线索本身当经历中心。先把它视为组织选择和问题现场留下的一部分证据，按由外到内主链反推：

1. 什么客户、市场、经营、运营或风险信号使公司愿意投入；为什么当时先做它而不是其他事项。
2. 谁会使用、受益、决策或承担成本，覆盖规模用账户、角色、用户、流程或业务量中的哪一层衡量。
3. 这项代码或任务试图改变什么异常、摩擦、风险、成本、体验或能力缺口。
4. 为什么当时把根因或突破口判断在这里，而不是相邻位置。
5. 哪些约束与真实备选方案塑造了实现路径，方案在阻力或新证据下如何演化。
6. 代码完成后系统、用户、团队或业务行为究竟发生了什么可证明变化，公司能否沿已确认机制获得价值，以及哪些变化不能归因于该工作。
7. 哪个判断可迁移到下一次类似问题，哪个判断重来会修改。

动作清单只有在帮助恢复上述链路时才有价值。若用户已经说明一组执行，不要换一种说法再次问“你亲自做了什么”；先推演这些线索可能位于哪些完整业务逻辑中，再问最能区分它们的上游问题。

用户授权读取精确代码文件、diff、测试、反馈、事故或决策记录时，从可见材料提取中性线索：修改前后的行为差异、失败分支、依赖/调用方、客户或使用角色、时间窗口、测试/日志、回退路径与决策表述。线索可以缩小候选业务逻辑，但不能由任何单一材料直接推出完整业务动机或收益。没有精确授权时只使用用户已经提供的线索，不扫描额外范围寻找故事。

## 先推演完整候选业务逻辑，再收敛到事实

开发者或新手常常准确记得局部事实，却不知道这些事实可能属于怎样的公司决策与价值系统。此时不要只问“为什么做”“有什么价值”，也不要给几个彼此割裂的价值标签。根据已有线索生成 2–4 条彼此可区分的 `candidate_business_case`，每条尽可能贯通：

```text
可能的组织目标或触发
  -> 可能的优先级理由与不做代价
  -> 可能受影响的角色、客户、用户或业务量
  -> 可能的价值获取/损失避免机制
  -> 当前线索所对应的具体瓶颈
  -> 能证实或推翻这条逻辑的材料
```

每条候选逻辑必须说明 `clue_basis`：它从用户哪条线索出发、经过了哪些推理；并说明 `distinguishing_evidence`：什么事实会使它成立或被排除。候选逻辑可以包含未知环节，但不能用空泛大词填满；缺失处明确写“待验证”。随后只问一个能淘汰最多候选逻辑或改变最大范围的分叉问题。

候选逻辑必须同时通过五项质量门：

- `end_to_end`：至少连接组织触发、优先级、影响对象/规模、价值机制、具体问题与验证信号；未知可以明确保留，不能在中途停成一个标签。
- `clue_grounded`：每个推理起点都能回指用户线索；行业常识只能解释“为什么值得考虑”，不能伪装成该公司的事实。
- `meaningfully_distinct`：不同候选至少在触发源、优先级逻辑或价值机制之一真正不同，不能把同一故事换三个标题。
- `falsifiable`：每条都指出能支持或排除它的记录、人物、指标、决策或事件。
- `ownership_bounded`：公司/团队的目标和选择与候选人本人的判断和贡献分开；完整不等于把所有决策都归给候选人。

`candidate_business_case` 是模型生成的完整思考脚手架，不是用户 claim，不进入事实台账，也不使用 `confirmed` 冒充结论。用户确认其中的最小事实后，把事实分别进入 `company_context_map`、四层经历地图和证据台账；被否定的候选应删除或标明排除，不能在后续文案中残留。

构造候选逻辑时可从以下镜头选择材料，但镜头只是内部零件，不能作为零散输出结束：

| 推理镜头 | 帮助补哪一段链路 | 可寻找的迹象 |
| --- | --- | --- |
| `company_strategy_priority` | 为什么公司现在投入，是否服务产品路线、重点客户承诺、经营目标、风险窗口或关键依赖 | 路线图、优先级记录、负责人/PM说明、客户承诺、事故/SLA、被阻塞项目 |
| `customer_commercial` | 客户反馈为什么值得行动，是否关系采用、成交、续约、扩容或服务体验 | 客户/CS/销售/支持记录、采用状态、合同节点；客户名称本身不是商业价值 |
| `reach_and_scale` | 影响的是实施团队、内部角色、客户账户、终端用户还是业务量，真实规模处在哪一层 | 账户、活跃角色、用户、申请/交易/工单、频次；任一单一口径只证明本层规模 |
| `economics_and_risk` | 公司如何获得收益或避免损失，是否降低人工/支持/接入成本、保护收入、控制 SLA/合规风险 | 成本与工时、支持量、成交/续约、故障与风险记录、复用后的边际投入 |
| `user_experience` | 等待、步骤、困惑、失败、可访问性或完成率是否改变 | 用户反馈、操作路径、失败场景、支持工单、可用性观察 |
| `product_business` | 是否解除关键流程阻塞、扩大可用范围、降低成本或控制风险 | 功能采用、流程完成、服务成本、合规/经营约束；没有证据时不得升级为增长或收入 |
| `engineering_quality` | 可靠性、性能、安全、可维护性、可扩展性或可观测性是否改善 | 错误/延迟、故障类型、测试、告警、复杂度、变更影响面、复用范围 |
| `delivery_collaboration` | 调试、发布、回滚、联调、交接或跨团队协作是否更顺畅 | 交付周期、返工、依赖等待、排障路径、发布风险、协作反馈 |
| `decision_learning` | 哪个约束、取舍或失败形成了可迁移判断 | 被否定的方案、新证据、策略转折、下次会改变的决策 |

若用户只说“这是最佳实践”“大家都这么做”或“应该这样写”，把重点从规范名称转回具体情境：该做法在这个项目里实际预防了什么失败、解除什么约束或支持什么后续变化。若没有可观察影响，就诚实保留为工程规范、质量护栏或交付要求，不制造业务收益。

候选逻辑可以完整推演，事实确认仍须逐层通过价值链，不能从任一局部线索直接跳到业务结果：

```text
局部线索或关键介入
  -> 系统/产物的直接变化
  -> 用户、团队或交付流程的行为变化
  -> 产品/运营指标变化
  -> 公司获得或保护的价值
  -> 财务或战略结果
```

每一条箭头都是独立的因果 claim。只走到当前证据能支持的最高一层：加校验可以先支持“阻止某类无效输入”，有工单或返工证据后才可能支持“减少某类返工”，不能直接写“提升转化”；拆分规则可以先支持“隔离站点差异”，有变更或回归证据后才可能支持“降低修改影响面”，不能仅凭模块化惯例声称效率提升。没有量化业务结果不等于没有价值，已确认的风险控制、能力解锁、质量护栏、认知负担降低或后续变化更安全都可以是有效结果。

### 事实层级与因果门

将线索按层级分开：`组织/客户语境 → 投入与优先级 → 能力或机制 → 实际覆盖与采用 → 行为/流程变化 → 产品或运营指标 → 公司价值 → 财务/战略结果`。任意一层的事实只证明本层；要上升一层，必须补充连接机制和证据。规模不等于采用，采用不等于收益，技术复用不等于经济杠杆，客户提出需求也不等于公司就应优先。缺业务数据时保留完整候选逻辑，但把未证实环节明确留作待验证，不给推测换一个肯定标题。

### 简短行为示例

用户只给出一项实现时，不要围绕实现连续追问。先推演若干完整但待验证的组织逻辑，例如它可能服务关键流程连续性、外部依赖风险治理，或运营/支持成本控制；每条都继续连接可能的优先级理由、影响对象、具体瓶颈和验证信号。然后问一个分叉问题确认真实触发源。用户确认后，沿被保留的业务逻辑逐轮核实优先级、规模、问题判断、取舍、结果与复盘。

## Question priority

公司经历先维护 `company_context_map`，再维护当前经历的四层地图，并选择会最大程度改变公司业务案、事实判断、问题解决链、职责归因或当前交付的一个缺口。不要按字段顺序机械问卷；上游答案推翻后续假设时，立即使受影响解释失效并重新排序。

如果已有线索允许多种完整解释，先生成或更新 `candidate_business_case`，再从中选择一个最能分叉的未知；不要绕过推演直接把“为什么做”原样丢回给用户。用户回答后，应同时更新所有受影响候选链，保留、合并或排除，而不是只填一个孤立字段。

每轮重新比较未解决项，并按当前最大阻断排序：

1. 解决影响范围最大的真实性、隐私或事实冲突。
2. 对公司经历，先确认进入组织优先级的真实触发信号与来源；“客户反馈了”仍需说明反馈为何值得行动。
3. 核实为什么当时先做它、与什么相邻事项或约束比较、不做的后果与机会成本；不是候选人决策时保持组织判断边界。
4. 区分请求/决策/实施方与实际受影响的客户、用户、角色或业务量，并确认公司预期通过什么机制获得或保护价值。
5. 澄清真正的问题、重要性及不处理的后果；任务表述不能替代问题定义。
6. 核实当时的问题判断依据、真实备选方案和取舍；没有就明确没有。
7. 找到哪个关键介入、阻力或调整最能解释问题状态为何改变。
8. 找到交付、使用、产品/运营及公司价值各层的结果证据，核实因果与外部因素；无精确指标时寻找一个可验证代理。
9. 补足最能体现思考演化的复盘反思。
10. 仅在影响贡献措辞、归因、冲突或面试可信度时，补足职责边界及其他事实细节。

同级候选中，选择最可能改变“能否写、贡献动词、选材或面试可信度”的一项。已 `confirmed` 的内容不再追问；普通缺口不阻断诚实交付时，明确标记即可。

当前问题还须同时满足：只处理一个核心未知；能区分至少两种可能解释或改变当前产物；锚定已有事实；允许回答“没有、未统计、未知”；不在问题中暗示理想答案。

## 高价值措辞取证

只有进入简历或招聘表达、且需要区分安全的高价值措辞时，才选择当前最能改变表达强度的一项核实：`ownership`（具体拥有的任务、交付物与决策权）、`coordination`（协调对象、推进动作与解除的阻碍）、`adoption`（是否交付、采用、上线或投入使用）、`before_after`（共同口径下的前后变化）、`metric_source`（指标定义、时间窗、来源和个人归因）。这些方向用于判断“负责/推动/主导/从 0 到 1/落地/优化/提升/降低”的证据门，不是经历深访的默认主线，不暗示答案，也不能在一轮拼成多问题。

## Experience coverage

深访过程中对公司经历同时追踪公司级业务案、四层地图与事实细节，但一个问题只处理一个核心未知。`key_intervention` 可以是判断、范围调整、实验、协作机制或实现，不预设“写代码最多”就是最有价值的部分。问题必须具体、易回答，并锚定用户已经提供的经历；可以给中性的回答范围或结构，也要允许“没有、未统计、未知”。不得给可照抄的虚构答案，不得暗示用户拥有尚未提及的成果、工具、客户、权限或领导责任。

## No-metric ladder

缺少精确指标时，按下列优先级寻找当前最适用的一个可验证代理，不要一次问完，也不要把代理改写成业务增长：

1. `scale`：真实规模
2. `frequency`：发生或交付频率
3. `coverage`：覆盖范围
4. `before/after`：有共同口径的前后变化
5. `delivery/adoption`：交付、验收或采用状态
6. `failure type`：处理或避免的故障类型
7. `steps/time saved`：减少的步骤或节省的时间
8. `response time`：处理或响应时效
9. `verified qualitative feedback`：可核验的定性反馈

任何数字、区间、估算、前后变化或定性代理都必须由用户确认其口径、时间窗、来源、个人/团队归因和是否可公开。未知就保持未知，不填默认值，不把团队指标归到个人，也不把“交付/采用/反馈”写成增长、转化或客户价值。

## Turn contract

证据仍不充分时，每轮按以下合同回复并等待：

1. 只简要说明本轮新确认的事实及其状态；必要时说明为何仍不能形成可投递经历。
2. 必要时先提供 2–4 条与当前线索直接相关的 `candidate_business_case`，每条贯通触发、优先级、影响规模、价值机制、具体问题与验证信号，并明确它们只是帮助识别真实经历的推测，不是用户事实。
3. 只提出一个最高信息增益问题。整轮只能有一个问句和一个问号。
4. 禁止长问卷、编号问题列表、多个问号、用分号或“以及/分别/同时”把多个独立问题拼成一问，也不得展示尚未提问的问题积压。
5. 收到回答后更新覆盖与证据台账，再重新排序；不要预先写强 bullet 等待用户追认。

单问题合同约束当前要求用户回答的取证问题。用户明确请求面试准备路线或追问图时，可以按 `review-rubrics.md` 展示未来可能面对的多条面试追问，但必须把它们标为“准备地图”而非本轮待答问卷，不得替用户填写答案；本轮仍只保留一个 `current_one_question` 推进证据。

问题可附一个简短的中性回答范围，但范围只能帮助定位同一个未知，不能顺带索取另一项事实。例如，用户只说“做了缓存”时，应问“当时触发缓存方案的首要矛盾，更接近响应速度、调用限制/成本，还是可用性？”，而不是同时追问实现、工具、难点、协作和结果。

## 两级就绪条件

`resume_claim_ready` 与 `interview_story_ready` 必须分开判断，避免为了写一条诚实 bullet 过度访谈，也避免把一条看似完整的 bullet 误当成经得住深挖的面试故事。职责边界是表达真实性的资格条件，不是经历价值的中心；经历深度主要由问题、判断、策略演化、结果归因和复盘决定。

- `resume_claim_ready`：当前表述所需的问题/背景、职责边界、本人具体动作或方法、结果或可验证交付、来源、归因和公开性均为 `confirmed`，且没有影响表述的冲突。未使用的地图字段可以保持未知。
- `interview_story_ready`：先满足 `resume_claim_ready`；公司经历中所有会影响立项原因、优先级、影响规模或价值解释的公司级字段，以及四层中所有会影响故事解释的字段，均为 `confirmed` 或已确认的“没有/未统计/不适用”；事实细节互相一致；候选人能区分公司/团队判断与本人判断、任务与问题、当时判断与事后解释、个人动作与团队过程、结果相关性与可证明归因。之后才可压缩成 STAR 或完整面试答案。

## 锚点经历准备顺序

当用户有多段经历且目标包含简历选材、排序或面试准备时，不平均深挖所有经历。先记录用户认为最有深度或最想被追问的经历；若用户未选择且选择会影响下一步，只问一个比较问题。再结合目标岗位相关性与当前证据，把一至三段候选交给 `resume-writing.md` 的锚点选择。

优先把最终锚点推进到 `interview_story_ready`。公司经历先准备立项触发、为什么现在优先、影响对象与规模、价值获得路径和交付后业务证据，再围绕简历实际使用的 claim 准备问题重要性、判断依据、真实备选、阻力与调整、结果归因、复盘和事实细节。普通支持性 bullet 只需达到请求所需的诚实交付门，不为了表面完整投入同等访谈轮次。

## Stop condition

达到用户请求对应的就绪级别后停止深访。只要求简历时按 `resume_claim_ready`；要求面试故事、STAR、追问准备或完整问题解决复盘时按 `interview_story_ready`。其余缺口必须显式标记，不得补齐。

如果事实已经足以支持用户所要求的诚实交付，并且用户已要求交付，就直接交付，不为了覆盖清单继续追问。若尚未达到门槛，明确说明目前不能形成可投递经历，只问当前一个最高信息增益问题并等待。
