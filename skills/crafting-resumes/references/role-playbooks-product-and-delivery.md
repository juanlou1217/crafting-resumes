# 产品与交付岗位 Playbook

适用于产品经理、AI 产品、B 端/平台产品、项目管理、实施与交付岗位。先以用户提供的 JD 和已确认事实为准，再用本表选择追问方向。

## 使用硬门

下表的关键词、指标、项目和问题都只是追问方向，绝不是候选人事实。不得据此补用户、客户、需求、原型、技术方案、上线状态、数字或结果。真实性门与单问题门优先于岗位匹配：只有 `confirmed` 事实可进入候选人事实产物；证据不足且影响下一步时，每轮正好问一个最高信息增益问题，不先给完整模板或候选 bullet。

**岗位词汇方向（仅用于提问与写作选择）**：需求澄清、优先级、方案取舍、跨职能推动、风险管理、验收、交付落地、采用。它们只是问题与表达方向，不是候选人事实；需要分别核实决策权、协调动作、交付/采用状态与归因后才能使用。

产品/交付岗位先用现有线索推演并核实组织为何投入：需求触发源、战略/客户语境、为什么现在优先、被影响的账户/角色/用户/业务量以及公司价值机制；再进入具体用户或业务场景、本人职责、判断与取舍、协作边界、验收和结果。泛技术栈通常不是第一问；任何单一产物、规模或语境事实都不能替代完整的公司决策与价值链，也不证明产品判断或交付所有权。

## 岗位追问方向

| 岗位族 | 优先核实的证据 | 可追问指标或代理 | 禁止捷径 |
| --- | --- | --- | --- |
| 产品经理 | 目标用户、业务问题、需求来源、本人职责、优先级/方案取舍、研发协作、验收与复盘 | 流程覆盖、需求采用、交付批次、操作步骤、处理时效、可核验反馈 | 把产物或功能范围直接写成用户/公司价值；把团队上线写成个人主导 |
| AI 产品 | 场景为何需要 AI、模型能力边界、数据/评测、人工兜底、成本与验收标准，以及本人产品责任 | 任务成功、采纳、响应、成本、评测覆盖；均须确认口径 | API 调用不等于 AI 产品任职；未确认不得补 Prompt 调优、Agent、RAG、幻觉治理或商业落地 |
| B 端 / 平台产品 | 使用角色、权限与流程、需求冲突、异常路径、迁移/上线约束、业务方和研发的责任边界 | 角色/流程覆盖、验收问题、交付范围、采用状态、反馈 | 由“画原型、跟验收”推断需求决策权、客户数、转化或效率提升 |
| 项目 / 实施 / 交付 | 范围、里程碑、依赖、风险、变更、资源协调、本人决策权、验收和交接 | 按期交付、缺陷类型、变更次数、覆盖范围、响应时效、验收状态 | 把参会、催办或协调写成推动；把项目总结果归为个人成果 |

## 证据选择顺序

1. 公司经历先确认需求为何进入公司视野、为什么当时先做、不做会影响什么，以及它与哪项客户承诺、产品策略、经营目标或风险要求相连。
2. 区分提出者、决策者、实施协作方与真正受影响的账户/角色/用户/业务量，再确认公司预期通过收入、续约保护、销售解锁、采用、成本、风险或平台杠杆中的哪条机制获得价值。
3. 确认“为谁、在什么流程中、解决什么真实问题”，避免从功能名称反推场景。
4. 再确认本人实际负责的交付物和决策边界，区分整理、建议、负责、推动与主导；公司选择优先做不等于候选人做了优先级决策。
5. 再确认一次具体取舍：冲突需求、资源/技术限制、异常路径或范围变更如何处理。
6. 最后确认协作、验收和分层结果来源；用户反馈、上线、覆盖或采用状态都不能自动改写成增长、转化、平台价值或客户价值。

## 单问题选择

若只知道局部产物或执行，公司经历先基于全部线索形成 2–4 条完整候选业务逻辑，再问一个能最大程度区分真实组织触发的问题，例如：“这次迭代当时进入公司优先级，最直接的触发信号是什么？”收到答案后再重新选择为什么先做、影响规模、价值机制、用户场景、职责、取舍、协作或验收中的一个缺口。整轮只能有一个问句和一个问号，不一次展示问题清单。
