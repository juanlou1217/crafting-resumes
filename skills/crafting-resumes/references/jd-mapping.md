# JD 证据映射

JD 词只能用于检索和组织已有事实，不能创造候选人事实。先读取 `evidence-and-truthfulness.md` 建立唯一事实台账；映射引用台账 claim 与来源，不复制出另一套事实。

## 适用性

| 输入 | 映射动作 |
| --- | --- |
| 有 JD 且有候选人证据 | 逐条映射；可诊断覆盖状态 |
| 仅 JD | 解析 JD 原文、权重和素材方向；不创建候选映射行，整个候选映射与匹配评分为 `N/A：缺少候选人证据` |
| 仅简历/经历，无 JD | 不创建 JD 映射行，整个 JD 映射与匹配评分为 `N/A：缺少 JD`；只做事实底稿与结构诊断 |
| 多 JD | 共用一份事实台账；每个 JD 独立解析、映射、版本和审查，再输出版本差异 |

岗位名称不等于明确 JD。没有目标方向的仅简历模式不得猜岗位、写 `X` 占位、生成假 bullet 或匹配结论；如果目标方向会影响下一步，只问一个目标方向。

## 映射记录

先用固定 JD 提取结构保存原文信息；未出现的字段写 `N/A：JD 未提供`，不得由岗位常识补齐：

| 提取字段 | 内容合同 |
| --- | --- |
| `target_role` | JD 原文中的岗位名称 |
| `seniority` | 明示职级、年限或候选层级 |
| `hard_gates` | 学历、年限、资格、地点等硬筛原文 |
| `core_responsibilities` | 核心职责原文及出现位置 |
| `required_skills` | 明示必需技能 |
| `preferred_skills` | 明示优先/加分技能 |
| `business_context` | 产品、客户、行业、团队或业务场景原文 |
| `deliverables` | 明示交付物与结果责任 |
| `implicit_interview_themes` | 由职责直接导出的待核实面试主题；标为分析，不当成候选人事实 |
| `ats_keywords` | JD 原词及其来源位置；不猜平台权重 |
| `rejection_risks` | JD 明示硬门或高权重缺口可能造成的筛选风险；不表示录用概率 |

提取结构描述岗位，不评价候选人。完成提取后，才按下表逐 requirement 绑定事实台账证据。

按 JD 的原始要求逐项记录，不用改写后的关键词替代原文：

| 字段 | 规则 |
| --- | --- |
| `jd_id` | 当前 JD 的稳定标识；多 JD 不得共用同一标识 |
| `jd_original` | 完整保留职责、技能或门槛的 JD 原文 |
| `requirement_type` | `hard_requirement`、`responsibility`、`skill` 或 `preference` |
| `weight` | `high`、`medium`、`low`；由 JD 的必需性、出现位置和职责核心性判断，并说明依据，不猜平台权重 |
| `candidate_evidence` | 引用一个或多个事实台账 claim；无证据写“无” |
| `source` | 每个候选证据的精确来源；只有技能清单时须明确写“技能清单，非项目/经历证据” |
| `status` | 只能是 `covered`、`weak`、`gap`、`do_not_force` |
| `reason` | 状态判断、个人/团队边界和仍缺的证据 |
| `resume_action` | `include`、`deprioritize`、`omit`；不得要求补写不存在的事实 |

映射表之外另列无法评分的原因、高权重风险和当前唯一问题；不得把 `N/A` 写入映射行的 `status` 字段或当成 0 分。

## 四种映射状态

| 状态 | 判定 |
| --- | --- |
| `covered` | 至少一个与要求直接相关、来源清楚且为 `confirmed` 的个人动作或结果；贡献强度与 JD 要求相符 |
| `weak` | 有 `confirmed` 的相邻、局部或可迁移证据，但缺少直接场景、深度、结果或职责强度；必须写明弱在哪里 |
| `gap` | 当前没有可用候选证据，或只有非 `confirmed` 线索；真实缺口可以保留并继续交付诚实版本 |
| `do_not_force` | 为匹配该要求只能推断事实、混淆学习与任职、升级贡献、挪用团队结果、暴露隐私或制造冲突；明确不写 |

技能清单只证明候选人声称接触该技能，不等于项目证据、熟练度或结果。它通常只能形成 `weak`；只有同一技能绑定到已确认的具体动作、来源和边界后，才可按证据判断 `covered`。`pending_confirmation`、`model_inference` 与 `conflict` 不得支撑 `covered`。

## 工作顺序

1. 填完固定 JD 提取结构，再原样拆出硬门、核心职责、技能和加分项；去重但保留每处原文来源。
2. 标权重与依据；高权重硬门无证据时单列风险，不用其他分数抵消。
3. 从唯一事实台账检索直接证据，再检索可迁移或学习/个人项目证据；三者不得互换。
4. 逐项选择四种状态，记录来源和边界。关键词只有绑定证据时才能进入简历。
5. 只把 `confirmed` 且满足当前产物披露范围的内容交给写作：`private_review_draft` 可使用用户本轮已确认、最小泛化并标记 `needs_redaction` 的事实；公开版本必须另有公开许可或确认脱敏。普通 `gap` 或 `weak` 不阻断诚实版本。
6. 用户补证或推翻事实时，先更新唯一台账，再使所有受影响映射、版本、差异和审查失效并重算。

## 多 JD 合同

禁止输出混合关键词的万能版。对每个 JD 分别输出：

- 独立的 JD 原文与权重表；
- 独立映射表及 `weak`/`gap` 风险；
- 仅调整选材、顺序和自然关键词的诚实版本；
- 独立六维审查。

最后输出版本差异表：

| 事实 claim | JD A：保留/顺序/措辞及原因 | JD B：保留/顺序/措辞及原因 | 不变的事实边界 |
| --- | --- | --- | --- |

同一 claim 的公司、日期、动作、数字、贡献强度和来源在各版本必须一致。差异只来自相关度与表达重点。不能由“需求访谈”补业务闭环，不能由“SQL 看板”补决策效果，也不能把“续费跟进”改成续费所有权。
