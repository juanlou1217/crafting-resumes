# 简历写作

写作只重组已确认事实，不提升事实强度。开始前通过真实性、冲突和适用于当前披露范围的隐私门；有明确 JD 时读取 JD 映射，只有目标岗位时使用岗位方向映射并明确无 JD 分。只有 `confirmed` 且允许进入当前产物的 claim 可以写入候选人陈述；`private_review_draft` 可用已确认、最小泛化且在独立风险说明中标记 `needs_redaction` 的事实，公开版本另须公开许可或确认脱敏。不得把该状态或提醒写进简历正文。

简短或含糊的用户原话必须语义保真，不能为了句子自然主动选择贡献梯级或动作解释。例如“做过需求访谈”不得改成“参与/负责需求访谈”；“做过 SQL 看板”不得改成“使用 SQL 制作/搭建看板”，除非用户确认究竟是制作、维护还是使用。证据不足时保留“做过”原词，或只在台账中记录，不能用所谓中性动词补全含义。

## 两阶段写作

1. **事实安全候选**：只用可进入当前产物的 `confirmed` claim，先形成不新增动作、工具、数字、结果或职责强度的候选表达；个人动作与团队结果分开。
2. **证据支持的价值与关键词优化**：读取 `keyword_evidence_map`，按 `professional-packaging-and-keywords.md` 选择证据能支持的最高表达，优化顺序、岗位语言和价值呈现。无证据关键词留在 `gap`、`do_not_force` 或 `next_question`，不硬塞进简历。

第二阶段不能修补第一阶段的事实缺口。至少保留一个事实安全版本和一个优化候选供风险检查；二者事实、时间线、归因与公开边界必须一致。

## 从事实到判断与定位

简历的说服力来自证据顺序，不来自自评。公司经历优先按已确认事实建立：

`组织为何投入 → 项目/模块解决什么问题 → 候选人的真实位置与判断 → 可验证结果`

组织和项目背景只解释问题分量，不能自动证明个人能力，也不能升级贡献动词。不得写无来源的“核心人才、技术专家、业务能力强”。任一环缺证据就省略；客户、经营数据与内部组织信息仍须通过保密门。

## 锚点经历优先

简历不是完整工作日志。写作前先让用户指出自己认为最有深度、最能代表思考的一至三段经历；若用户没有明确选择，根据适用的公司级业务案和四层经历地图提出候选，再在该选择会影响排序时只问一个问题。用户的主观重视程度记为 `candidate_priority`，它决定需要认真评估和准备什么，但不能单独证明经历深度、岗位相关性或结果强度，也不得被 Skill 静默忽略。未被用户排序的经历保持 `unset`，Skill 可以评估其证据和岗位价值，但不得替用户发明“中/低偏好”。

锚点经历按以下顺序判断，不计算伪精确总分：

1. 先通过真实性、冲突、归因、隐私与当前披露范围门。
2. 有 JD 时确认它是否支撑高权重职责、技能或面试主题；无 JD 时按已确认目标方向判断。高权重硬门仍优先，不能只因故事精彩而掩盖岗位缺口。
3. 对公司经历，先检查公司级业务案能否把需求触发、为什么现在优先、影响对象与规模、价值获得机制及交付后的业务证据连成相干链；任何单层语境、规模、能力或过程事实都不能直接当作更高层价值，若只能列出若干价值标签则仍视为 `partial`。
4. 检查四层地图是否体现清楚的问题、当时判断或取舍、策略演化、结果证据与复盘；深度来自公司语境和问题解决思考链，不来自代码量、项目规模或华丽措辞。
5. 检查该经历能否自然引出有价值的“公司为什么做、为什么先做、影响谁和多大、依据是什么、比较过什么、如何调整、怎样验证、重来会怎样”追问，并且候选人能够基于证据回答。
6. 在同等条件下，优先更相关、更新近、与其他锚点不重复的经历。

使用三级锚点状态：

- `not_ready`：用户重视或 Skill 识别到潜力，但拟使用的公司价值、问题、判断、结果、来源或其他资格门仍缺关键证据；只能作为 `anchor_candidate` 继续深挖，不能在最终简历中当作已合格锚点前置。私审结构稿可以标明 `provisional_first`，但必须在简历正文之外说明其未就绪。只因用户偏爱而未验证深度时，始终称“用户优先锚点候选/暂定候选”，不要称“核心锚点、正式锚点、最强经历”或断言它“应该前置”。若仅公司语境未知，但一条不声称公司价值的能力/交付 claim 已满足事实门，它仍可按该较弱 claim 判断 `frontload_ready`；不能把未知业务案写成肯定价值。
- `frontload_ready`：相关候选表述已满足 `resume_claim_ready`，可安全放在简历前部或经历首条；若面试准备未完成，必须在独立风险说明中标记。
- `interview_anchor_ready`：先满足 `frontload_ready`，再满足 `interview_story_ready`，且已生成与简历原文逐字对应的面试追问图。优先把这种经历作为最终锚点。

若用户重视的经历与目标岗位相关性较弱，不要擅自删除：说明冲突，将其作为次级锚点、补充项目或私有面试素材；目标岗位的硬门和直接证据仍须在前部清楚出现。若一段经历只是任务多、技术名词多，但缺少问题、判断或结果证据，不把它误判为深度经历。

项目组合不按固定数量凑栏目。正式锚点之外，只保留能补充不同且已确认信号的技术平台、基础设施、主动改进、跨域、协作或管理经历；同类项目优先证据更强、与 JD 更相关的一项。项目数量、公司名气或技术栈数量都不代表资历和目标薪资。

### 前置方式

- 简历前部用一至两个至少为 `frontload_ready` 的锚点证据建立第一印象；`not_ready` 只能作为结构稿中的暂定候选，不能伪装成最终排序。摘要只在能自然压缩合格锚点证据时使用，不写抽象自评。
- 工作/实习经历保持清晰的逆时间顺序，不为“显得重要”改写日期；在同一经历内部，将锚点 bullet 放第一条。
- 高相关的项目、作品或转行证据可放入前置的“精选项目/相关项目”栏目，但不重复粘贴同一经历，也不伪装成任职经历。
- 删除或压缩“参与会议、配合开发、完成日常需求”等低区分度流水账；它们只有在解释锚点经历的约束或协作时才保留。
- ATS 纯文本无法依赖加粗时，用栏目顺序、经历顺序和 bullet 顺序保持同样的锚点优先级。

### 让面试官产生高质量追问

公司锚点 bullet 应在有限篇幅中优先呈现“真实公司/客户触发或影响规模 + 为什么值得优先 + 核心问题/约束 + 关键判断或取舍 + 可验证的分层结果”中证据最强的部分，再按岗位需要写改变问题状态的介入。不是每条都强塞全部要素，也不要求候选人声称公司决策权。不要故意藏掉关键事实、制造悬念或使用空泛大词；信息密度本身应自然引出公司为何投入、影响谁、价值如何发生、方案依据、替代方案、策略调整、结果归因和复盘追问。

面试准备不平均分配给所有 bullet。先围绕一至三段锚点经历补齐适用的公司级业务案、四层地图、事实细节和公开证据，再用 `review-rubrics.md` 生成与简历原文对应的追问图。按“主要准备/次要准备/基础核对”等定性顺序分配精力，不凭空给出 70% 等伪精确时间比例。若候选人无法解释被前置 claim 的公司语境、优先级、影响规模、问题、判断、取舍或结果，就先继续深挖、降级措辞或取消前置，不能把未准备好的强 claim 当视觉中心。

## 不可补全的事实

不得从动作、行业惯例、JD 或相邻内容推断公司、正式岗位名、职级、项目名、工具、日期、数字、职责或结果。

- “在某公司实习”只能证明实习场景，绝不能补成“前端开发实习生”等正式岗位名。
- “做了页面”不能自动补接口联调、需求拆解、上线验证或工程化建设。
- 课程项目的三人团队只说明团队规模；个人仅拥有已确认的模块、动作和结果。
- 目标岗位名独立呈现，不得改写成历史岗位名。

未知的可选字段直接省略；影响理解但不阻断诚实交付时，可以在修改说明或私有证据包中明确“待补”，不得在公开简历中写成事实或保留占位符。

## HR-first 选材

按 HR 约 10–20 秒扫读组织信息：

1. 让目标方向、候选人背景和一至两个 `frontload_ready` 或 `interview_anchor_ready` 锚点证据在前部可识别。
2. 在不改变时间线的前提下，将更相关、更有公司语境与问题解决深度且能承受追问的经历与 bullet 前置；删除低相关重复和任务流水账。
3. 让公司为何投入、为什么优先、影响谁和多大、如何获得价值中已确认且最相关的一项在前置锚点里可见；不用任何单层事实替代完整价值证明。
4. 用自然中文描述真实场景和个人贡献，避免“赋能、抓手、闭环、全链路、沉淀”等无证据黑话，也避免统一模板腔和无依据自评。
5. 同一 JD 词只在最有证据的位置出现；再次出现必须对应不同事实。

摘要不是必填项。若没有足够已确认的背景与匹配点，省略摘要，不写“结果导向”“具备优秀能力”等空话。

## 禁止在简历正文中写元话语

简历正文只呈现候选人的背景、动作、方法和结果，不呈现写作过程、证据判断或风险提示。不得把真实性与归因边界写成自我辩护式免责声明，包括但不限于：

- “不归因为本人增收成果”；
- “不声称带来转化提升”；
- “当前证据只支持……”；
- “该数字仅表示……”；
- “未确认公开披露权限前不可投递”。

遇到不能归因、不能公开或证据强度不足的信息时，直接按以下顺序处理：

1. 删除不必要的团队经营数据、内部指标或无法解释的数字；
2. 只写本人已确认的动作、判断和交付，不把并列的团队结果连接为个人因果；
3. 必须保留业务背景时，使用自然的事实陈述，不在句尾追加否定式免责说明；
4. 将保密风险、证据状态和待确认事项放入独立的修改说明、风险报告或事实台账，不放入简历姓名区、公司介绍、经历 bullet 或项目正文；
5. 用户没有要求风险报告时，不主动把内部审查文字写进简历文件，尤其不得用可见提示或 HTML 注释污染交付正文。

归因边界必须通过句子结构体现。例如，个人只做了漏斗分析时，写“结合生成与上传漏斗定位主要损耗环节”，不要写成“提升转化率”，也不要再补一句“该结果不归因于本人”。

## Bullet 组合

锚点 bullet 从可用证据中选择并自然组合：

`公司/客户触发或真实规模（适用且已确认） + 为什么值得优先 + 核心问题/约束 + 判断/取舍 + 关键介入/策略演化 + 可验证的分层结果`

支持性 bullet 可使用：

`必要背景 + 个人动作 + 方法/工具 + 可验证结果`

两种结构都不强制填满四段。锚点优先呈现思考链，支持性 bullet 补充必要交付；缺任一部分时只写已确认内容，不得用常识补句。优先满足：

- 主语边界清楚：本人动作与团队结果分开；
- 动词不超过贡献梯级证据；
- 方法具体但不堆工具；
- 技能与工具 claim 能回指真实场景，并能解释适用的关键机制、边界或验证；无法承受追问的“精通/源码级”表述降级或删除；
- 数字带口径、时间窗、来源和必要的“约/区间”限定；
- 结果只证明其本身：交付或验收不等于增长，团队结果不等于个人归因。

如果事实只支持“封装请求错误处理”，就写该动作；不能为了贴 JD 自动写“完成接口联调”。如果团队项目中本人负责前端页面，只能呈现这些页面和已确认的个人优化结果，不能把三人项目整体写成个人主导。

## 公共简历与私有证据包

两层共用同一事实台账，但披露范围不同：

- **公共简历/ATS/招聘沟通**：只含可公开、必要、已确认且已脱敏的信息；删除内部客户名、内部链接、本地路径和未公开经营数据。
- **私有证据包/面试准备**：保存 claim 来源、指标定义、个人/团队边界、可回答的追问和风险；`restricted` 信息仍不得因“私有”自动扩大授权。

公开层的精简不能改变事实；私有层不能成为把未确认信息写入公开层的借口。

## ATS 纯文本版

使用单栏、线性、可复制文本；关键信息不得依赖表格、图片、图标、文本框、页眉页脚、隐藏文字或关键词堆叠。采用标准栏目并按实际存在的信息保留：

1. 姓名与已确认联系方式（可选）
2. 目标岗位
3. 个人摘要（可选）
4. 核心技能（只列真实技能，关键词自然）
5. 工作/实习经历
6. 项目经历
7. 教育经历

栏目顺序可按身份调整：

- 校招/实习：教育背景可前置；随后放最相关的实习、项目、竞赛或校园证据。
- 社招：最近且相关的工作经历优先；教育通常后置。
- 转行：目标方向明确，将直接证据、可迁移证据、学习/个人项目证据分开，不伪装直接任职。

公司、正式岗位、项目、学校、联系方式等未提供时省略或在私有修改说明中标记待补；最终公共版不得出现方括号、`X`、示例值或待确认成句。

## 完稿检查

- 每个事实能回指台账来源且状态为 `confirmed`。
- 每个 JD 关键词能回指一条具体证据；技能清单不冒充项目证据。
- 用户指定的深度经历已进入锚点选择，保留、降级或不前置都有明确原因，没有被静默忽略。
- 公司锚点的立项触发、为什么优先、影响规模和价值机制已按证据呈现或明确留作准备缺口；没有让语境、投入、能力、覆盖、采用、指标和公司结果之间只靠措辞跳层。
- 前部一至三个锚点均为 `frontload_ready`；作为重点面试素材的锚点达到 `interview_anchor_ready` 或已明确列出准备缺口。
- 面向读者的 Markdown 简历和经历总结已按 `emphasis-and-highlighting.md` 突出少量锚点问题、判断/策略和结果；ATS 纯文本代码块不放 Markdown 加粗标记。
- 没有新造的岗位名、动作、数字、效果或团队归因。
- 时间线未因相关度排序而改变。
- 中文易扫读，无机械句式和 AI 黑话。
- ATS 版与定向版事实完全一致，只改变格式。
- 多 JD 版本只改变选材、顺序和重点，并有差异表。
